Kernels

Part 10 of Block Diffusion Rooflines: two rewrites, of the experts and of global attention, and what they change in efficiency, throughput and quality.

Part 10 of Block Diffusion RooflinesPrevious: 9 · The measurement stackNext: 11 · Conclusion

Even with the engine fixed, two components of TD's step remain far below their rooflines: the routed experts, and global attention at head dimension 512. In this chapter, we explain why each loses time, rewrite both, and measure what the rewrites change in efficiency, throughput and quality. Along the way, we define the hardware terms that we add to those of Part 9.

Terms

Rewriting a kernel requires a closer look at the hardware. The H200 is a Hopper GPU, and we use the following terms throughout this chapter.

  • SM (streaming multiprocessor): one of the 132 independent processors of the chip, each with its own tensor cores (the matrix-multiply units), registers and shared memory.
  • CTA (cooperative thread array, or thread block): a group of threads that runs on one SM and shares its shared memory; a kernel launch is a grid of CTAs. A cluster is a group of CTAs, here two, that run at the same time on different SMs and can read and write each other's shared memory.
  • Registers and shared memory: 256 KB of registers and about 227 KB of shared memory per SM. Matrix-multiply accumulators live in registers; operand tiles are staged in shared memory before the tensor cores read them.
  • Tile and pipeline stage: a CTA computes one block of the output, its tile, and streams the operands it needs through shared memory in chunks. With two or more stages (buffers), the next chunk loads while the tensor cores work on the current one; with one, loading and computing alternate.
  • TMA (Tensor Memory Accelerator): a copy engine on each SM that moves a whole rectangular tile from memory to shared memory with one instruction.
  • FP8 scaling: an FP8 number has a narrow range, so a block of values shares a scale \(\delta\), and \(x\) is stored as \(\mathrm{round}(x/\delta)\). The scale can be per tensor or per row ("per token").
  • Warp, warpgroup: 32 threads that execute together, and 4 warps that issue one tensor-core instruction together.
  • Epilogue: the last stage of a GEMM kernel, which turns the accumulators of a tile into the output (scaling, activation, conversion) before writing it.
  • Atomic addition: an addition to a memory location that is safe when several CTAs add to it at once.

The experts

An MoE layer of DiffusionGemma has hidden size \(d = 2816\), \(E = 128\) experts of width \(f_E = 704\), and \(k = 8\) experts per token. For a token \(x_i\) routed to expert \(e\) with weight \(p_{i,e}\),

\[ a_{i,e} = \mathrm{gelu}\bigl(x_i W_{g,e}^{\top}\bigr) \odot \bigl(x_i W_{u,e}^{\top}\bigr), \qquad y_i = \sum_{e} p_{i,e}\, a_{i,e} W_{d,e}^{\top}: \]
\[ \begin{gathered} a_{i,e} = \mathrm{gelu}\bigl(x_i W_{g,e}^{\top}\bigr) \odot \bigl(x_i W_{u,e}^{\top}\bigr),\\[4pt] y_i = \sum_{e} p_{i,e}\, a_{i,e} W_{d,e}^{\top}: \end{gathered} \]

a first GEMM with the gate and up matrices \(W_g, W_u\) and a second with the down matrix \(W_d\). Consider \(N\) tokens touching \(U\) experts, with \(\mu = Nk/U\) rows per touched expert on average. The layer does \(F = 6Nk\,d f_E\) FLOPs and reads \(Q = 3U d f_E\) bytes of FP8 weights, so its intensity is \(F/Q = 2\mu\). Since the empirical ridge point is 340 FLOP/byte, the layer is compute-bound above about 170 rows per expert. At the measured routing, TD reaches this point from batch 16 on, and at batch 8 at context 64k.

vLLM's two expert GEMMs are not slow: profiled at batch 32, they take the same time as those of our expert kernel below. Instead, the time is lost between them, in passes that write intermediate tensors to memory and read them back.

Our expert kernel, moe_ws, makes four changes.

  • Weights rewritten once. The gate and up matrices are padded with zero rows from 704 to 768 and interleaved in blocks of 128, and \(W_d\) is padded to 768 columns. The padding is exact: a padded column has gate and up equal to 0, so \(a = \mathrm{gelu}(0)\cdot 0 = 0\), which meets a zero column of \(W_d\). A tile of the first GEMM then holds 128 gate columns next to their 128 up columns, so the activation can be applied in registers.
  • First GEMM with the activation. Each CTA takes 128 rows of one expert (64 at batch 1–2, where a layer holds at most 4,096 rows), gathers the corresponding rows of \(x\), which one light kernel has quantised to FP8 with one scale per token beforehand, and applies the activation in registers.
  • One pass to quantise \(a\). The FP8 scale of a row of \(a\) needs its maximum over all 768 columns, which no single tile sees, so a light kernel converts \(a\) to FP8 with one scale per row.
  • Second GEMM with the reduction. The epilogue multiplies each row by its routing weight and adds it into the token's output with atomic additions. A token's 8 contributions meet in the L2 cache, so the 369 MB of rows per (token, expert) pair at batch 32 never reach memory.

With these changes, the expert path takes 19–28% less time per pass, and the TD step 4–8% less (Table 14). We use the expert kernel for TD only: an AR step sends 1–64 tokens through a layer, and there it is 9% slower. GSM8K on 250 problems is 96.8% with and without it.

Of course, our kernel is not the best one can do. The best kernel available at the same shape is cuBLAS on one large GEMM with all \(Nk\) rows stacked, which needs no padding per expert. At batch 32, it runs the first GEMM at 0.93 of the empirical FP8 ceiling, and the second, with the width padded to 768, at 0.64 counting only its real FLOPs. Weighted by their FLOPs (two thirds and one third), the two GEMMs together run at 0.81 of the empirical roofline. This reference sets the experts' target efficiency in Definition 7 (Part 9).

Nsight Compute, NVIDIA's kernel profiler, locates the rest of the gap inside the two Triton GEMMs:

  • First GEMM: It keeps the tensor cores busy 69% of the time, because with one CTA per SM nothing loads the next tile while a tile finishes.
  • Second GEMM: It is bound by latency: the tensor cores are busy 41% of the time, with two CTAs per SM.

What would close the gap is what cuBLAS has and Triton does not expose on Hopper: separate producer and consumer warps, TMA loads shared across a two-CTA cluster, and an epilogue that overlaps the next tile.

Global attention at head dimension 512

Five of the 30 layers attend globally, with \(n_q = 16\) query heads, \(n_{kv} = 2\) key/value heads and head dimension \(h = 512\). In a denoising pass, the \(b = 256\) canvas queries of a sequence attend to its \(C + b\) keys, so

\[ F = 4\,b\,(C + b)\, h\, n_q, \qquad Q \approx \kappa^c s_{kv}\,(C + b)\, h\, n_{kv}, \qquad \frac{F}{Q} = \frac{4\,b\,n_q}{\kappa^c s_{kv}\,n_{kv}} = b\,I_{\mathrm{attn}} = 2048 \ \text{FLOP/byte}, \]
\[ \begin{gathered} F = 4\,b\,(C + b)\, h\, n_q, \qquad Q \approx \kappa^c s_{kv}\,(C + b)\, h\, n_{kv},\\[4pt] \frac{F}{Q} = \frac{4\,b\,n_q}{\kappa^c s_{kv}\,n_{kv}} = b\,I_{\mathrm{attn}} = 2048 \ \text{FLOP/byte}, \end{gathered} \]

This intensity is 14 times the ridge point of the attention ceiling, \(\hat\pi_{\mathrm{attn}}/\hat\beta \approx 148\). Hence, the kernel should run at the attention ceiling. In practice, FlashAttention 4 runs at 296–357 TFLOP/s here, against 700–729 at head dimension 256 on the same rows. The cause is the head dimension. Indeed, a CTA keeps its output rows in registers in FP32, \(4M_qh\) bytes for \(M_q\) rows, i.e., 128 KB at \(M_q = 64\), half of the register file. In addition, in shared memory the query tile and one stage of keys and values take

\[ \underbrace{64 \cdot 512 \cdot 2}_{\text{queries}} + \underbrace{64 \cdot 512 \cdot 2}_{\text{keys}} + \underbrace{64 \cdot 512 \cdot 2}_{\text{values}} + \underbrace{64 \cdot 64 \cdot 2}_{\text{scores}} \ \text{bytes} = 200\ \text{KB}, \]
\[ \begin{gathered} \underbrace{3 \times 64 \cdot 512 \cdot 2}_{\text{queries, keys, values}} + \underbrace{64 \cdot 64 \cdot 2}_{\text{scores}}\\[4pt] = 200\ \text{KB}, \end{gathered} \]

so a second stage does not fit in 227 KB. Hence, loading cannot overlap compute, and Nsight Compute finds the tensor cores busy 36% of the time.

Our pair kernel, attn512, splits the head dimension across the two CTAs of a cluster. With the query, key and value tiles \(\mathbf Q = [\mathbf Q_0\ \mathbf Q_1]\), \(\mathbf K = [\mathbf K_0\ \mathbf K_1]\), \(\mathbf V = [\mathbf V_0\ \mathbf V_1]\) split at column 256,

\[ \mathbf Z = \mathbf Q\mathbf K^{\top} = \mathbf Q_0\mathbf K_0^{\top} + \mathbf Q_1\mathbf K_1^{\top}, \qquad \mathbf O_i = \mathrm{softmax}(\mathbf Z)\,\mathbf V_i \quad (i = 0, 1). \]
\[ \begin{gathered} \mathbf Z = \mathbf Q\mathbf K^{\top} = \mathbf Q_0\mathbf K_0^{\top} + \mathbf Q_1\mathbf K_1^{\top},\\[4pt] \mathbf O_i = \mathrm{softmax}(\mathbf Z)\,\mathbf V_i \quad (i = 0, 1). \end{gathered} \]

Figure 38

Splitting the head dimension leaves room for a second pipeline stage.

Shared memory per thread block, in KB, against the 227 KB of one SM. FA4 at head dimension 512 holds full-width tiles and fits one stage; a block of the pair holds half-width tiles and fits two stages of 64 keys plus two exchange buffers. With 80-token KV pages the fastest configuration uses the room differently, for one stage of 80-key tiles loaded by TMA (Table 15).

Each CTA thus solves a head-dimension-256 problem, which is small enough for two stages or for larger tiles of keys. This comes at the cost of one exchange per tile of keys: each CTA sends its partial scores into the partner's shared memory and waits for the partner's. Per tile of \(M_q\) query rows and \(M_k\) keys, a CTA does \(4M_qM_k\,(h/2)\) FLOPs and sends \(M_qM_k\) FP16 scores, i.e., 512 FLOPs per byte crossing between the SMs. Without the exchange1, the pair would run at 711–723 TFLOP/s. With it, in the configuration with 64-key tiles and two stages, each tile waits about 0.5 µs for synchronisation and 0.67 µs for the transfer, against 1.5 µs of tensor work. The fastest exchange uses 16-byte asynchronous stores into two alternating buffers2.

The KV cache is stored in pages of a fixed number of tokens. When the page size equals the kernel's tile of keys, keys and values can be loaded by TMA. Hence, TD uses pages of 80 tokens with the pair kernel, whose fastest configuration has one stage of 80-key tiles. In dedicated engine runs outside the grid of Parts 8–11 (Table 15), global attention then runs 1.36–1.37 times faster than FlashAttention 4 at its best page size. Timed alone on the engine's layout, the pair kernel reaches 0.71–0.74 of the attention ceiling (0.73 on average at the three shapes of Table 15), so the engine loses little beyond the kernel itself. Note that at batch 1, where a pass holds fewer than 512 queries, the pair kernel is slower than FlashAttention 4, which keeps those calls.

What the two kernels change

Both kernels raise their components' efficiency without reaching their targets of Definition 7 (Part 9). At batch 8 and above:

  • Global attention: Its efficiency moves from 0.45–0.56 to 0.58–0.70, against a target of 0.73.
  • Experts: Their efficiency moves from 0.27–0.38 to 0.33–0.51, against a target of 0.81.
  • Whole TD step: It moves from 0.43–0.50 to 0.46–0.61 of its roofline, against 0.43–0.69 for AR at the same points.

  • Context 4k: 6.8 ms of the step are saved: 5.6 in the experts and 2.4 in global attention, less 1.2 ms that the head, the dense layers and time outside the model lose.
