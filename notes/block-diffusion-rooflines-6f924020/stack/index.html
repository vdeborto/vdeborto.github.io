The measurement stack

Part 9 of Block Diffusion RooflinesPrevious: 8 · Effective rooflinesNext: 10 · Kernels

Part 8 gives a roofline time for each component of a forward pass. This chapter describes how the measured time of a pass in vLLM is split into the same components, so that the two can be compared, and the three defects of the stock engine that these measurements exposed.

Terms

The measurements below use four notions from GPU programming.

  • Kernel: one function launched on the GPU, such as a matrix product or an attention computation. One forward pass of the model launches several hundred kernels.
  • Eager mode: the CPU launches the kernels of a pass one by one, from Python. Each launch costs a few microseconds of CPU time, which at small batch is comparable to the kernel itself.
  • CUDA graph: the sequence of kernels of one pass, recorded once ("capture") and then replayed with a single launch, which removes the per-kernel launch cost.
  • Profiler trace: the GPU's record of every kernel that ran, with its name, start time and duration.
Figure 27

In eager mode the GPU waits for each launch; a CUDA graph runs the kernels of a pass back to back.

Four kernels of one forward pass, as in Part 8's small GEMMs: launching a kernel costs the CPU a few µs, and with 64 tokens or fewer a projection runs for 5–12 µs, so in eager mode the GPU waits a large share of the time. A CUDA graph replays the recorded sequence of kernels with one launch.

From an engine run to a time per component

The roofline of Part 8 gives a time for each component of a pass: the experts, the dense layers, window and global attention, and the vocabulary head. To compare it with the GPU, the measured time of a pass must be split into the same components. The harness roofscope does this for each measured point, a decoder at a batch size \(B\) and a context \(C\), in three steps.

Figure 28

Each term of a component's efficiency is read at a different level of the serving stack.

Left: what runs when the engine serves a point \((B, C)\), from the prompts down to the accelerator. Middle: the four records roofscope takes, each at the level where the quantity exists. The engine's wall clock gives the step time \(t\); a counter in the model gives the experts touched, \(U\); the profiler's trace of kernels gives the time \(t_c\) of each component; and the microbenchmarks of Part 8 give the ceilings \(\hat\pi_c\), one per kind of kernel, and \(\hat\beta\) of the accelerator. Definition 7 combines them: the FLOPs \(F_c\) and bytes \(Q_c\) of a component, counted by the cost model of Parts 1–7 at the point \((B, C)\) and at the measured \(U\), and the ceilings give its roofline time \(\tau_c\), which is compared with \(t_c\). Each \(\tau_c\) uses the expert count of the profiled window, where \(t_c\) is read, and the step's \(\tau\) that of the timed window, where \(t\) is read. The rest of this section describes the two windows of a run (Figure 29) and the labelling of kernels (Figure 30).

Running a point. The engine processes \(B\) prompts of \(C\) tokens with CUDA graphs, as in serving, one forward pass at a time. Each prompt is a passage of a PG-19 book followed by a request for a long essay about it, in the model's chat template, so that both models write ordinary prose in their chat distribution; \(C\) is the prompt length. The first canvas is produced while the prompts are prefilled and the second is a warm-up; roofscope then records two consecutive windows of 30 passes, two canvases each (48 steps each for AR, whose windows are placed at the same context, \(C + 1024\) at their middle). The TD windows are therefore the third to sixth canvases of the answer, which most answers still fill. During the first window the profiler records every kernel with its duration. During the second the profiler is off, because it slows the passes down, and only the wall-clock time per pass is kept; its mean is the step time \(t\). Throughout both windows, a counter in each MoE layer records how many tokens each expert receives in each pass.

Figure 29

One measured point: a profiled window for the kernels, a timed window for the step time.

TD at one batch size \(B\) and context \(C\): the windows are the third to sixth canvases of the answer; the first is produced during the prefill. The profiler slows the passes down, so the step time comes from the second window, where it is off. For AR the windows are 48 steps each, after 976 warm-up steps, which put AR's context at the middle of the windows at TD's.

Labelling kernels. roofscope wraps each module of the model (attention, MoE layer, vocabulary head, and so on) in a named profiler range, and every kernel is recorded with the range it was launched from. Under a CUDA graph the whole pass is launched at once, so each kernel is recorded with its name but only with the range of the whole pass. The same point is therefore run once more in eager mode, where each kernel is launched from its own module. A kernel of the graph run takes the module of the eager kernel with the same name and launch shape, counted in order of occurrence. The vocabulary head and the sampler run outside the graph and keep their own ranges. Kernels generated by the compiler, whose names start with triton_, fuse the small operations between modules and have no eager counterpart of the same name; they are counted as outside the model, and make up 5–14% of TD's kernel time and 4–19% of AR's.

Figure 30

Each kernel of the graph run takes its module from the eager run.

A stretch of one layer, with simplified kernel names. In the eager run each kernel is recorded inside the profiler range of the module that launched it; in the graph run only inside the range of the whole pass. The same kernel can serve several modules, as the FP8 GEMM does here, so the match counts occurrences. Each module then belongs to one component. The compiler fuses the norm with its neighbours into a kernel of another name, which has no eager match and counts as outside the model.

Summing by component. The labelled kernel times are summed into five components: experts, dense GEMMs and router, window attention, global attention, and vocabulary head with sampler and self-conditioning. Kernels that belong to none of them (norms, rotary embeddings, residual additions, activation quantisation) are summed as "outside the model". The step time minus the total kernel time is "idle", the time the GPU waits. Part 8 gives each component's roofline at the measured routing, and Definition 7 compares it with the component's measured time.

Definition 7Efficiency and recoverable time

In short. A component's efficiency is its empirical roofline over its measured time; its recoverable time is what remains above the time of the best kernel available at its shape.

With \(t_c\) the measured time of component \(c\) per step and \(t\) the step time, the efficiency of the component and of the step are

\[ \eta_c = \frac{\tau_c}{t_c}, \qquad \eta = \frac{\tau}{t} = \frac{\sum_c \tau_c}{t}, \]

where time outside the model and idle time count in \(t\) but have no roofline. Each \(\tau_c\) is evaluated at the expert count of the profiled window, in which \(t_c\) is measured, and \(\tau\) at that of the timed window, in which \(t\) is measured (the \(U^{\mathrm{meas}}\) of Definition 6); the two windows hold different canvases, so \(\sum_c \tau_c\) equals \(\tau\) only approximately. The target efficiency \(\eta^\star_c\) is that of the best kernel available at the same shape, timed alone: for TD's experts 0.81 (cuBLAS on all rows stacked, Part 10), for AR's experts 0.58 (vLLM's own expert kernel timed alone at batch 32), for global attention 0.73 (the pair kernel of Part 10 alone, at the engine's layout); for the other components it is 0.8. The recoverable time of a component is \(\Delta t_c = \max(0,\ t_c - \tau_c/\eta^\star_c)\), and the recoverable time of the components outside the model is their whole time.

Four checks guard the numbers:

  • Attribution: at most 0.7% of kernel time is left without a component at any point (median over repeats), and 1.2% in any single run.
  • Full batches: a point at which the engine could not keep all \(B\) sequences in memory is excluded.
  • Same campaign: the stock-kernel reference that Part 10 compares with ran in the same campaign, on the same prompts, as the measurements.
  • Quality: every change to the engine is checked on GSM8K and IFEval, since a faster kernel that changes the output measures nothing.

Three defects of the stock engine

The first runs of DiffusionGemma in stock vLLM 0.28.0 left TD far below its roofline. Following the largest components down to their kernels found three defects, which the measurements of Parts 8–11 have fixed.

Stale causal flags under CUDA graphs

A TD pass is bidirectional while it denoises a canvas and causal when it commits it, so DiffusionGemma passes the attention kernel one flag per sequence. vLLM 0.28.0 kept these flags in a boolean buffer and converted it to 32-bit integers at every step; the conversion creates a new tensor, at a new address.

Figure 31

A replayed CUDA graph reads the memory it saw at capture, so a tensor recreated at every step is never read.

DiffusionGemma passes a causal flag per sequence to the attention kernel: 0 for a bidirectional denoising pass, 1 for the causal commit pass. In vLLM 0.28 the flags lived in a bool buffer converted to int32 at every step; under CUDA graphs the attention kernels kept reading the copy made at capture.

vllm/model_executor/models/diffusion_gemma.py, the fix

self._causal_buf = torch.zeros(
    self.max_num_reqs, dtype=torch.int32, device=device   # was dtype=torch.bool
)

With the flags of the capture step, commit passes ran bidirectionally and wrote wrong keys and values into the cache. A probe inside the graph found up to 14 of 15 passes reading a wrong flag, and GSM8K accuracy under CUDA graphs was 34%, against 96% with the fix. Timings were also wrong, since a bidirectional pass costs more than a causal one. vLLM 0.32.0 allocates the buffer as int32 upstream.

Window attention over the whole cache

25 of DiffusionGemma's 30 layers attend to a sliding window of the last 1,023 tokens. FlashAttention 4, the attention kernel vLLM uses here, accepts a causal flag per sequence; for a bidirectional sequence it reset the range of key blocks to the whole sequence, discarding the window, and then masked the blocks outside the window. A window layer therefore read the whole cache in every denoising pass, at a cost that grows with the context instead of staying constant.

vllm_flash_attn/cute/flash_fwd_sm90.py, both sites (producer and consumer)

# before: if const_expr(self._mDynamicCausal is not None):
if const_expr(self._mDynamicCausal is not None and not self.is_local):
    # per-sequence causal flag; for a bidirectional sequence the kernel
    # resets the key-block range to the whole sequence

At batch 16 and context 16k, window attention fell from 52.2 to 5.1 ms per pass. The override is still in the FlashAttention commit that vLLM 0.33.0 ships.

A sampler that reads the logits many times

Each denoising pass samples every one of the 256 canvas positions from 262,144 logits, after a soft cap. The stock sampler applied the soft cap and then made a separate pass over the logits for each of the maximum, the sum, the entropy, the argmax, the inverse-CDF sample and the probabilities kept for self-conditioning. One Triton kernel now does it in one pass: the soft cap bounds the logits, which replaces the running maximum, and partial sums per block of the vocabulary serve both the normalisation and the inverse CDF. At batch 16 the sampler fell from 21 to 7 ms per pass, and a \(\chi^2\) test of its samples against the reference gives \(p = 0.53\).

A fourth defect was in the harness itself. The vLLM wheel ships compiled bytecode that Python does not revalidate against the source, so a patched source file can silently keep running the old code; every patch now deletes the bytecode of the file it edits, and the flag fix is checked at run time by a probe inside the graph.
