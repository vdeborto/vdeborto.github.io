The measurement stack

Part 6 of Block Diffusion Rooflines: how every kernel of a step is timed and attributed, three defects of the stock engine and one of the harness, and where the stock kernels stand.

Part 6 of Block Diffusion RooflinesPrevious: 5 · Empirical rooflinesNext: 7 · Kernels

Part 5 gives a roofline time for each component of a forward pass; comparing it with the GPU needs a measured time for the same components. This chapter describes how roofscope splits the measured time of a pass in vLLM into these components, and the three defects of the stock engine, and one of the harness, that the measurements exposed.

Terms

The measurements below use a few notions from GPU programming, collected here with those already met in Part 5.

  • Kernel: one function launched on the GPU, such as a matrix product; a forward pass of the model launches several hundred.
  • Eager mode: the CPU launches the kernels of a pass one by one, from Python, at a few microseconds of CPU time each (Figure 22).
  • CUDA graph: the sequence of kernels of one pass, recorded once ("capture") and then replayed with a single launch, which removes the per-kernel launch cost.
  • Profiler trace: the GPU's record of every kernel that ran, with its name, start time and duration.
  • GEMM: a general matrix multiplication, the kernel of every linear layer.
  • HBM: the GPU's main memory, read at the bandwidth \(\beta\); L2 is a smaller on-chip cache in front of it.
  • Prefill: the forward pass over a prompt, which writes its keys and values into the cache before the first token or canvas.
  • Triton: a compiler for GPU kernels written in Python.
  • cuBLAS: NVIDIA's matrix-multiply library.
  • CUTLASS: NVIDIA's template library for writing matrix-multiply kernels.
Figure 22

In eager mode the GPU waits for each launch; a CUDA graph runs the kernels of a pass back to back.

Four kernels of one forward pass, as in Part 5's small GEMMs: launching a kernel costs the CPU a few µs, and with 64 tokens or fewer a projection runs for 5–13 µs, so in eager mode the GPU waits a large share of the time. A CUDA graph replays the recorded sequence of kernels with one launch.

From an engine run to a time per component

The components of Part 5 are the experts, the dense layers, window and global attention, and the vocabulary head. For each measured point, a decoder at a batch size \(B\) and a context \(C\), our harness roofscope splits the measured time of a pass into these components in three steps.

roofscope
The harness behind Parts 5–8: it runs vLLM on Modal, records every kernel and every routing decision, and turns them into the components, rooflines and efficiencies of these chapters. The code excerpts quote it at commit 8ef0040, with their line numbers; the repository is not yet public.
Figure 23

Each term of a component's efficiency is read at a different level of the serving stack.

Left: what runs when the engine serves a point \((B, C)\), from the prompts down to the accelerator. Middle: the four records roofscope takes, each at the level where the quantity exists. The engine's wall clock gives the step time \(t\); a counter in the model gives the experts touched, \(U\); the profiler's trace of kernels gives the time \(t_c\) of each component; and the microbenchmarks of Part 5 give the ceilings \(\hat\pi_c\), one per kind of kernel, and \(\hat\beta\) of the accelerator. Definitions 5 and 7 combine them: the FLOPs \(F_c\) and bytes \(Q_c\) of a component, counted by the cost model of Parts 1–4 at the point \((B, C)\) and at the measured \(U\), together with the ceilings, give its roofline time \(\tau_c\) (Definition 5), which Definition 7 compares with \(t_c\). Each \(\tau_c\) uses the expert count of the profiled window, where \(t_c\) is read, and the step's \(\tau\) that of the timed window, where \(t\) is read. The rest of this section describes the two windows of a run (Figure 24) and the labelling of kernels (Figure 25).

Running a point. The engine processes \(B\) prompts of \(C\) tokens each with CUDA graphs, as in serving, one forward pass at a time. Each prompt is a passage of a PG-19 book followed by a request for a long essay about it, in the model's chat template, so both models write ordinary prose in their chat distribution.

After a warm-up canvas, roofscope records two consecutive windows of 30 passes, two canvases each: the third to sixth canvases of the request whose prefill ends last, centred at context \(C + 1024\), where AR's windows are also centred (Figure 24). The other requests start decoding earlier and keep generating while it is prefilled, so at large \(BC\) they are further on: at batch 64 and context 4k, 63 of the 64 requests are on average 3.4 canvases ahead. The rooflines use the context of the last request. The two windows serve different purposes:

  • First window: The profiler records every kernel with its duration.
  • Second window: The profiler is off, because it slows the passes down; the mean wall-clock time per pass, less the time of roofscope's own routing kernels, is the step time \(t\).

Throughout both windows, a counter in each MoE layer records how many tokens each expert receives in each pass.

Labelling kernels. roofscope wraps each module of the model (attention, MoE layer, vocabulary head, and so on) in a named profiler range, and every kernel is recorded with the range it was launched from. Under a CUDA graph, however, the whole pass is launched at once, so each kernel is recorded only with the range of the whole pass. We therefore run the same point once more in eager mode, where each kernel is launched from its own module, and each kernel of the graph run takes the module of the eager kernel with the same name and launch shape, counted in order of occurrence. The vocabulary head and the sampler run outside the graph and keep their own ranges. Compiler-generated kernels, whose names start with triton_, fuse the small operations between modules and have no eager counterpart of the same name; we count them as outside the model, and they make up 5–14% of TD's kernel time and 4–19% of AR's.

Figure 25

Each kernel of the graph run takes its module from the eager run.

A stretch of one layer, with simplified kernel names. In the eager run each kernel is recorded inside the profiler range of the module that launched it; in the graph run only inside the range of the whole pass. The same kernel can serve several modules, as the FP8 GEMM does here, so the match counts occurrences. Each module then belongs to one component. The compiler fuses the norm with its neighbours into a kernel of another name, which has no eager match and counts as outside the model.

Summing by component. We sum the labelled kernel times into these five components, with the router counted with the dense GEMMs and the sampler and self-conditioning with the vocabulary head. Kernels that belong to none of them (norms, rotary embeddings, residual additions, activation quantisation) are summed as "outside the model". The step time minus the total kernel time is "idle", the time the GPU waits.

Definition 7Efficiency and recoverable time

With \(t_c\) the measured time of component \(c\) per step and \(t\) the step time, the efficiency of the component and of the step are

\[ \eta_c = \frac{\tau_c}{t_c}, \qquad \eta = \frac{\tau}{t}, \]

where time outside the model and idle time count in \(t\) but have no roofline. Each \(\tau_c\) is evaluated at the expert count of the profiled window, in which \(t_c\) is measured, and \(\tau = \sum_c \tau_c\) at that of the timed window, in which \(t\) is measured (the \(U_{\mathrm{meas}}\) of Definition 6). Since the two windows hold different canvases, the sum of the profiled \(\tau_c\) differs slightly from \(\tau\). The target efficiency \(\eta^\star_c\) is that of the best kernel available (for AR's experts, the vLLM kernel that the engine runs), timed alone at representative shapes (one shape, or for global attention the mean of three), where we timed them, and 0.8 otherwise; each target is applied at every point:

  • TD's experts: 0.81, cuBLAS on all rows stacked (Part 7);
  • AR's experts: 0.58, vLLM's own expert kernel timed alone at batch 32, with 43 experts touched1;
  • TD's global attention: 0.73, the pair kernel of Part 7 alone, at the engine's layout;
  • every other component: 0.8, with no standalone reference.

The recoverable time of a component is \(\Delta t_c = \max(0,\ t_c - \tau_c/\eta^\star_c)\); time outside the model and idle time are recoverable in full.

Four checks guard the numbers:

  • Attribution: at most 0.7% of kernel time is left without a component in any run of the measured points.
  • Full batches: a point at which the engine could not keep all \(B\) sequences in memory is excluded.
  • Same campaign: the stock-kernel reference that Part 7 compares with ran in the same campaign as the measurements, on the prompts of their first repeat.
  • Quality: every change to the engine is checked on GSM8K (grade-school maths word problems) and IFEval (verifiable instruction following), since a faster kernel that changes the output measures nothing. Part 7 says which kernel configuration each check used.

Three defects of the stock engine, and one of the harness

Our first runs of DiffusionGemma in stock vLLM 0.28.0 left TD far below its roofline. Tracing the largest components to their kernels revealed three defects, fixed in every measurement of Parts 5–8.

Stale causal flags under CUDA graphs

A TD pass is bidirectional while it denoises a canvas and causal when it commits it, and the sequences of a batch need not be at the same pass, so DiffusionGemma passes the attention kernel one flag per sequence. vLLM 0.28.0 converted the boolean buffer of these flags to 32-bit integers at every step, which creates a new tensor at a new address, whereas a CUDA graph replays the memory addresses recorded at capture; every replay therefore read the flags of the capture step.

Figure 26

A replayed CUDA graph reads the memory it saw at capture, so a tensor recreated at every step is never read.

DiffusionGemma passes a causal flag per sequence to the attention kernel: 0 for a bidirectional denoising pass, 1 for the causal commit pass. In vLLM 0.28 the flags lived in a bool buffer converted to int32 at every step; under CUDA graphs the attention kernels kept reading the copy made at capture.

vllm/model_executor/models/diffusion_gemma.py, the fix

self._causal_buf = torch.zeros(
    self.max_num_reqs, dtype=torch.int32, device=device   # was dtype=torch.bool
)

A pass could therefore run with the wrong mask: a commit pass bidirectionally, which wrote wrong keys and values into the cache, or a denoising pass causally. A probe inside the graph found up to 14 of 15 passes reading a wrong flag2, and GSM8K accuracy under CUDA graphs was 34%, against 96% with the fix3. Timings were also wrong, since a bidirectional pass costs more than a causal one.

Window attention over the whole cache

25 of DiffusionGemma's 30 layers attend to a sliding window of the last 1,023 tokens. FlashAttention 4 (FA4), the attention kernel vLLM uses here, accepts a causal flag per sequence; for a bidirectional sequence, it reset the range of key blocks to the whole sequence, discarding the window, and then masked the blocks outside it. Hence, a window layer read the whole cache in every denoising pass, at a cost that grows with the context instead of staying constant4.

A sampler that reads the logits many times

Each denoising pass samples each of the 256 canvas positions from 262,144 logits, after a soft cap. The stock sampler wrote the soft-capped logits in FP32 and then swept them about seven times: temperature scaling, Gumbel noise, the sampled and the plain argmax, the log-softmax, its exponential and the entropy.

We replace it with one Triton kernel per pass, with one instance per canvas position (\(256B\) in all), which samples by inverse CDF and reads the full row of logits once for all of these. Its sums of exponentials per block of the vocabulary serve both the normalisation and the inverse CDF, so drawing the sample reads only one block again. At batch 16, the sampler fell from 21 to 7 ms per pass, and a \(\chi^2\) test of its samples against the reference gives \(p = 0.53\).

Stale bytecode in the harness

The vLLM wheel ships compiled bytecode that Python does not revalidate against the source, so a patched file can silently keep running the old code. Two guards prevent it: every patch deletes the bytecode of the file it edits, and every run asserts that the flag buffer is int32.
